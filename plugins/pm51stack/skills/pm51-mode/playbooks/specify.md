# Specify

The decisions are made. Write them down as a spec, as slices, or as a map. Then build only if the user asked you to build.

1. Restate the destination and the check that would prove the whole effort, not only the next slice.
2. When `docs/agents/issue-tracker.md` is missing and you are about to publish a spec, tickets, or a map, read `setup-matt-pocock-skills` and follow it before you publish. The forge is already the `forge` line in `.cursor/rules/pm51stack.mdc`. Follow the forge section of [../project-config.md](../project-config.md). Ask GitHub or GitLab again only when that line is missing.
3. When the work is bigger than one session and the destination is still foggy, read `wayfinder` and follow it. Resolve one decision at a time.
4. When the conversation is already settled, read `to-spec` and follow it. Publish the spec. Do not open a new interview.
5. When the spec should become buildable work, read `to-tickets` and follow it. Each ticket names an observable outcome, the check, and what it blocks on. A ticket that is only a table, only an endpoint, or only a screen is not a slice.
6. When the user asked you to build, open the feature playbook with the spec and the tickets. That playbook builds the ticket graph.

Reply with the link or path of the spec and the ticket list.
